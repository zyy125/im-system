# Frontend Operation Logic Spec

这份文档不是“当前页面代码做了什么”的流水账，而是后续前端重写时应遵守的交互规范。

目标：

1. 让后续 AI 或人工重写前端时，不把聊天工具最关键的交互逻辑写偏。
2. 让页面行为尽量接近市面上的聊天工具，例如 QQ、微信、企业微信等常见 IM 产品。
3. 在保持当前后端接口协议不变的前提下，定义一套更优雅、更稳定的前端操作逻辑。

---

## 1. 总体交互原则

前端交互应遵循以下原则：

- 聊天优先
  - 用户进入系统后，最重要的是尽快进入“可聊天”的状态。
- 状态连续
  - 会话、消息、未读、历史加载、重连后的恢复都要尽量连续，不让用户觉得“数据断层”。
- 乐观但可回滚
  - 发送消息时允许前端先显示，但必须给失败态和重试手段。
- 与主流聊天工具一致
  - 会话排序、已读、历史分页、失败重试、隐藏会话恢复等行为尽量贴近用户习惯。
- 业务语义优先于 UI 美化
  - 后续 UI 可以重画，但交互语义不能乱。

### 1.1 信息架构原则

主界面应参考 QQ 一类聊天工具，区分为两个一级视图：

- 消息栏
  - 关注“最近在聊什么”
  - 展示当前用户 `visible = true` 的活跃会话
- 联系人栏
  - 关注“我可以和谁聊”
  - 再细分为：
    - 好友列表
    - 群聊列表

这两个视图不是两套独立数据体系，而是同一套关系数据的两种展示方式：

- 单聊好友在底层上对应唯一单聊会话
- 群聊列表在底层上对应当前用户加入的群会话
- 区别只在于展示目标不同，而不是领域模型不同

设计原因：

- 当前后端已经以 `Conversation / ConversationMember / Message` 为核心
- 单聊在成为好友时就会自动创建或恢复会话
- 因此“好友”和“单聊会话”天然是一一对应关系，没必要在前端再人为拆成两套互不相干的对象

## 2. 最终确定的操作逻辑

下面这些规则视为已经定稿，后续前端重写时默认遵守。

### 2.1 主界面结构

主界面推荐采用：

- 左侧一级导航：
  - 消息
  - 联系人
- 联系人页二级导航：
  - 好友
  - 群聊

各视图语义如下：

- 消息
  - 展示“当前活跃且可见的会话”
  - 单聊和群聊混排
  - 带未读数、最后一条消息、最后活跃时间
- 联系人 / 好友
  - 展示“当前好友关系仍有效的单聊对象”
  - 本质上是单聊会话的联系人视图
  - 即使该单聊在消息栏被隐藏，这里仍然要能看到并重新打开
- 联系人 / 群聊
  - 展示“当前仍是成员的全部群聊”
  - 即使该群在消息栏被隐藏，这里仍然要能看到并重新打开

### 2.2 注册与登录

- 注册成功后，自动登录。
- 自动登录成功后，直接进入聊天主界面。
- 不需要用户注册后再手动点一次登录。

设计原因：

- 这更符合现代聊天工具的直觉体验。
- 可以减少一次无意义操作。

### 2.3 会话隐藏与恢复

- 隐藏会话只影响当前用户自己的会话列表展示。
- 隐藏不会删除消息，也不会删除会话本身。
- 隐藏不会影响联系人栏：
  - 单聊隐藏后，好友仍在“联系人 / 好友”里
  - 群聊隐藏后，群仍在“联系人 / 群聊”里
- 以下情况会自动恢复显示该会话：
  - 当前用户再次从好友列表打开对应单聊
  - 当前用户再次从群聊列表打开群
  - 对方发来新消息
  - 当前用户再次在该会话中发送新消息

设计原因：

- 这符合聊天软件中“折叠/隐藏入口，不丢失聊天记录”的常见逻辑。

### 2.4 会话列表排序

- 会话列表始终按“最后一条消息时间”倒序排序。
- 最新活跃的会话排在最上面。
- 如果最后消息时间相同，再按后端返回的会话稳定字段兜底排序，避免顺序抖动。

设计原因：

- 这是绝大多数聊天工具的默认行为。

### 2.5 历史消息加载

- 打开会话时，先加载最近一页历史消息。
- 用户向上滚动到聊天框顶部时，继续加载更早消息。
- 历史消息按从旧到新渲染。
- 每次加载更早历史时，页面应保持滚动位置稳定，不能突然跳到底部或顶部。
- 界面需要有明确的“加载中”提示。
- 当没有更多历史时，需要有明确的“没有更多消息”提示。

设计原因：

- 这就是微信、QQ 这一类产品的标准交互方式。

## 3. 推荐采用的完整交互规则

以下规则用于补齐你还没明确拍板的部分。我这里已经按“更合理、更像成熟聊天工具”的方式替你定好了。

### 3.1 登录后的初始化

登录或自动登录成功后，前端应按以下顺序初始化：

1. 保存 token
2. 获取当前用户信息
3. 拉取消息栏列表、好友列表、群聊列表、申请列表
4. 建立 WebSocket 连接
5. WebSocket 建立成功后，再次刷新侧边栏数据

说明：

- 第二次刷新侧边栏的目的，是让实时连接建立后的在线状态、离线补推、最近消息摘要尽快同步。
- 这里的“侧边栏数据”不再只指会话列表，也包括联系人栏里的好友和群聊。

### 3.2 默认首页行为

- 登录成功进入聊天主界面后，默认展示会话 tab。
- 如果会话列表非空：
  - 默认不自动打开第一条会话
  - 等用户自己选择
- 如果会话列表为空：
  - 显示空状态，引导用户添加好友或发起会话

设计原因：

- 自动打开第一条会话容易产生误已读和误打断。

### 3.3 点击会话的行为

点击会话后：

1. 高亮当前会话
2. 更新聊天区标题
3. 首次进入该会话时加载最近一页历史消息
4. 历史加载完成后渲染聊天区
5. 若当前会话存在未读消息，则推进已读

补充规则：

- 点击当前已经打开的会话，不重复发起首屏历史加载
- 但应允许用户通过上滑继续加载更早历史

### 3.4 从好友列表发起聊天

点击好友列表里的“发起会话”后：

1. 直接拿到该好友对应的单聊 `conversation_id`
2. 若该会话当前被隐藏，则调用打开会话逻辑恢复显示
3. 自动切换到消息 tab
4. 自动进入该会话

更推荐的前提是：

- 成为好友时，后端已经自动创建单聊会话
- 好友列表接口直接返回该好友对应的 `conversation_id`

这样前端后续可以统一按 `conversation_id` 驱动聊天打开，不再依赖单独的 `OpenDirect` 接口。

### 3.5 从群聊列表打开群

点击群聊列表里的某个群后：

1. 直接使用该群的 `conversation_id`
2. 若该群当前在消息栏中被隐藏，则调用打开会话逻辑恢复显示
3. 自动切换到消息 tab
4. 自动进入该群会话

### 3.6 消息发送逻辑

发送消息时采用“乐观插入 + 状态机”的方式。

前端一条消息应有以下本地状态：

- `sending`
  - 刚点击发送，已经本地显示，但还没确认成功
- `sent`
  - 服务端已确认或回流到本地
- `failed`
  - 发送失败，需要提示用户处理

最终交互规则：

- 用户点击发送后，消息立即出现在聊天区
- 初始状态显示为 `sending`
- 如果服务端回流成功，则转为 `sent`
- 如果发送失败，则转为 `failed`
- `failed` 消息应支持：
  - 手动点击重试
  - 或者右键/长按后重发

设计原因：

- 这是成熟聊天工具更常见、更自然的体验
- 比“发送失败直接消失”优雅得多

### 3.7 WebSocket 断线时的发送策略

采用如下规则：

- WebSocket 断开时，用户仍然可以继续输入消息内容
- 但点击发送后：
  - 消息先进入本地列表
  - 状态标记为 `failed` 或 `waiting`
- 连接恢复后：
  - 不自动静默重发所有失败消息
  - 由用户主动点击重试

为什么这样定：

- 完全禁止输入会让体验很硬
- 自动后台重发所有消息又容易引入重复发送、状态不透明的问题
- 更稳妥的方式是：允许本地保留消息，但最终是否重发交给用户决定

这比“断线时完全不能发”更像成熟产品，也比“后台默默重试”更安全。

### 3.8 收到新消息时的未读规则

未读数只统计“别人发给我、且我当前还没读掉”的消息。

具体规则：

- 自己发的消息不算未读
- 当前未打开的会话收到新消息：
  - 未读数增加
- 当前打开的会话收到新消息：
  - 默认自动已读
  - 不增加未读数

这是你当前系统最适合的默认规则。

### 3.9 当前打开会话的自动已读条件

这里我替你定成：

- 只要会话当前正在打开，并且聊天窗口处于可见状态，就自动推进已读。

不再要求：

- 必须滚动到底部
- 必须额外点击某个位置

设计原因：

- 当前项目还是单页 Web 前端，不需要过度复杂化“阅读确认”的判断
- 对大多数聊天工具来说，只要你正在看这个会话，就会被视作已读

后续如果你想更严格，也可以再升级为：

- 只有窗口在前台 + 已滚到底部 + 新消息进入可视区域才推进已读

但当前阶段没必要先做这么重。

### 3.10 离线补推消息的显示逻辑

离线补推消息应遵循：

- 先进入本地消息缓存
- 再与首屏历史页 merge 去重
- 打开会话前，这批消息仍然算未读
- 打开会话后，统一进入正常已读逻辑

注意：

- 离线补推不是完整历史
- 首次打开会话仍然要补拉最近一页历史

### 3.11 顶部上滑加载的 UX 细节

用户把聊天框滚到顶部附近时：

- 自动触发加载更早历史
- 聊天框顶部显示“加载中”
- 加载成功后隐藏“加载中”
- 若没有更多历史，顶部显示“没有更多消息”
- 这个提示不应该是打断式弹窗，而应是聊天列表内的轻提示

### 3.12 会话摘要更新规则

会话列表中的 `last_message` 更新规则：

- 只要收到或发送了一条新消息，就刷新该会话摘要
- 该会话移动到列表顶部
- 但如果当前收到的是旧离线补推消息，不应错误地把它当成“最新消息”覆盖更晚的新消息

也就是说：

- 前端在更新会话摘要时，要区分“真正的新消息”和“历史补齐/离线回填消息”

### 3.13 在线状态展示

在线状态建议继续展示在：

- 会话列表
- 好友列表

申请列表可以不作为重点展示区，但如果已有数据同步能力，可以保留。

优先级建议是：

1. 会话列表
2. 好友列表
3. 申请列表

### 3.14 好友申请流程

发送好友申请后，前端必须区分后端返回的不同业务结果：

- `pending`
  - 正常发送成功，显示“等待对方处理”
- `already_friends`
  - 提示“你们已经是好友”
- `auto_accepted`
  - 提示“已自动成为好友”
  - 同时刷新消息栏、好友列表、申请列表

同意申请后：

- 自动刷新侧边栏数据
- 自动切到消息 tab
- 不强制自动打开会话

拒绝申请后：

- 只刷新申请列表

### 3.15 隐藏会话的交互建议

点击“隐藏会话”后：

- 当前会话从消息栏移除
- 聊天区回到“请选择会话”
- 联系人栏中的好友或群聊入口仍然保留
- 不弹确认框也可以
- 但如果后续你想更稳，可以加轻量确认

我建议当前先不加二次确认。

原因：

- 隐藏不是删除
- 风险比删除低
- 二次确认会降低操作效率

### 3.16 退出登录

退出后必须清空：

- token
- 当前用户信息
- 消息栏列表
- 好友列表
- 群聊列表
- 申请列表
- 当前会话
- 本地消息缓存
- 历史分页状态
- 已读重试状态

然后回到登录页。

### 3.17 WebSocket 自动重连

采用以下规则：

- 如果 token 仍然有效，则在断线后自动重连
- 重连间隔可固定 3 秒，也可逐步退避
- 重连成功后：
  - 自动刷新消息栏与联系人栏
  - 自动恢复离线补推逻辑

推荐你后续升级成：

- 第 1 次 1 秒
- 第 2 次 3 秒
- 第 3 次 5 秒
- 之后上限 10 秒

这样会比固定 3 秒更优雅。

## 4. 前后端职责安排

这部分用于明确：上述产品模型落地后，前端该负责什么，后端该负责什么。

### 4.1 前端职责

前端应把主界面拆成三类数据视图：

- 消息栏数据
  - 来源是“当前可见会话列表”
  - 用于展示未读、最后消息、最近活跃排序
- 好友联系人数据
  - 来源是“好友 + 对应单聊会话”
  - 用于发起或恢复单聊
- 群聊联系人数据
  - 来源是“当前有效群成员关系”
  - 用于打开或恢复群会话

前端不应自己推导这些领域规则，例如：

- 不要前端自己根据好友 ID 拼接会话 ID
- 不要前端自己判断某个群是否应该在联系人栏消失
- 不要把 `visible=false` 理解成“关系删除”或“退群”

前端更适合做的是：

- 维护当前选中的 `conversation_id`
- 维护消息栏与联系人栏的本地状态
- 合并 WS 实时消息、离线补推和历史分页
- 根据后端返回结果更新会话显示与未读状态

### 4.2 后端职责

后端应继续坚持“以会话为中心”的建模方式：

- 单聊和群聊统一归入 `Conversation`
- `ConversationMember.visible` 只控制消息栏是否展示
- 联系人栏是否能看到某个对象，应由“好友关系是否有效 / 群成员状态是否有效”决定

后端要保证这些语义稳定：

- 成为好友时，自动创建或恢复唯一单聊会话
- 隐藏会话时，不删除关系，不删除历史，不影响联系人栏
- 打开会话时，只恢复 `visible=true`，不新造重复会话
- 群聊隐藏后仍然保留成员关系，直到退群、被移除或群解散

### 4.3 推荐的数据接口安排

为了让前端真正优雅地实现上述模型，推荐后端把接口职责整理成下面这样：

- `GET /api/v1/conversations`
  - 只负责消息栏
  - 返回当前用户 `visible=true` 的活跃会话
- `GET /api/v1/friends`
  - 负责联系人 / 好友
  - 推荐扩展返回：
    - `conversation_id`
    - 可选的 `conversation_visible`
  - 这样前端点好友时可以直接按 `conversation_id` 打开
- 新增 `GET /api/v1/conversations/groups`
  - 负责联系人 / 群聊
  - 返回当前用户仍为活跃成员的全部群聊
  - 这里不应受 `visible` 限制

### 4.4 当前项目下的最小改造方案

如果想尽量少改后端，也可以分两步走：

第一步：

- 保留现有 `GET /api/v1/conversations`
- 保留现有 `GET /api/v1/friends`
- 好友列表返回 `conversation_id`
- 好友列表里点击聊天时，直接调用 `POST /api/v1/conversations/{id}/open`
- 这样可以先把“联系人栏”产品形态做出来

第二步：

- 给群聊增加独立“联系人 / 群聊”列表接口
- 前端统一改成“进入聊天只依赖 `conversation_id`”
- 这样单独的 `OpenDirect` 就可以直接下线

### 4.5 最终建议

从长期优雅性看，推荐你项目最终收敛成下面这套模式：

- 前端：
  - 所有聊天窗口都由 `conversation_id` 驱动
  - 好友和群聊只是不同联系人视图
- 后端：
  - 所有消息、历史、已读、隐藏、恢复都围绕会话处理
  - `friend_id` 只用于关系管理，不再作为聊天主入口

这样你的系统会更像成熟 IM，而不是“好友系统外面套一个聊天功能”。

## 5. 后续前端重写时最容易写错的地方

以下是必须重点提醒 AI 的风险点。

### 5.1 把离线补推误当成完整历史

错误写法：

- 收到离线消息后，就认为这个会话历史已经完整了

正确写法：

- 离线补推只是补一段未读消息
- 首次打开会话仍然要请求最近一页历史

### 5.2 把自己发的消息算成未读

错误写法：

- 当前会话里只要来了消息就加未读

正确写法：

- 未读只统计发给当前用户的消息

### 5.3 上滑加载时不保持滚动位置

错误写法：

- prepend 旧消息后，滚动条直接跳动

正确写法：

- 加载前记录高度
- 加载后修正 `scrollTop`

### 5.4 把隐藏会话写成删除聊天记录

正确语义必须是：

- 只隐藏入口
- 不删消息
- 不删会话

### 5.5 把发送失败静默吞掉

错误写法：

- 用户看到消息已显示，但其实后端没成功
- 页面也不给任何失败提示

正确写法：

- 必须有 `failed` 状态
- 必须允许用户重试

### 5.6 把当前会话收到消息误判为未读

当前推荐逻辑：

- 当前正在看的会话默认自动已读

### 5.7 把历史分页写成一次性全量加载

错误写法：

- 打开会话直接拉全量历史

正确写法：

- 首屏一页
- 上滑继续翻页

## 6. 交给 AI 重写前端时必须附带的硬约束

后续把前端交给 AI 重写时，建议明确写进提示词中的约束如下：

- 不能改变现有后端 API 协议
- 不能改变 WebSocket event type
- 不能把离线补推当成完整历史
- 不能把自己发的消息算作未读
- 不能把隐藏会话实现成删除聊天记录
- 必须支持历史消息分页上滑加载
- 必须支持消息发送失败态与手动重试
- 注册成功后必须自动登录并进入聊天页
- 消息栏必须按最后一条消息时间排序
- 联系人栏中的好友和群聊不受 `visible` 影响
- 当前打开会话收到新消息时默认自动已读

## 8. 一句话总结

后续前端应做成这样：

- 注册成功即进入聊天
- 消息栏始终按最新消息排序
- 联系人栏包含好友和群聊两个视图
- 打开会话先看最近消息
- 上滑继续加载更早历史
- 当前打开会话默认自动已读
- 消息先本地显示，再根据结果呈现发送成功或失败
- 隐藏会话不等于删除聊天，且隐藏后仍可从联系人栏重新打开

这套交互逻辑已经足够接近常见聊天工具，也和你当前后端能力基本匹配。
